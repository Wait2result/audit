Главное:

1. **«Хочу покушать» → «Где искать?» — это не баг отрисовки, а сочетание трёх причин.**
   В умном поиске нет раздела заведений: есть только доставка, и она жёстко ставит `hasDelivery=true`.
   Модель честно не понимает фразу (`intent: unknown`, уверенность 0,2), а сервер отвечает общим списком разделов из реестра.
2. **Варианты «Где искать?» не работают вообще (0/8).**
   По нажатию приложение отправляет ту же фразу с подсказкой экрана, а сервер игнорирует подсказку, если модель вернула `unknown`.
   Кроме того, контекст сессии запоминает раздел из подсказки. Следующее нажатие может дать чужой раздел («Кино» → доставка)
   или ошибку разбора. После скрытого повтора человек через 8–10 секунд снова видит «Где искать?».
3. **Объявления, кино и новости работают хорошо.** Поиск структурированный, данные реальные,
   выдача совпадает с прямым запросом к сервису 79/79, цепочка «до миллиона → автомат → бензин» держится.
4. **Доставка — слабое место.** «Хочу заказать пиццу» даёт ошибку или «не поддерживается».
   Блюдо, которое модель отнесла к несуществующей плитке витрины, теряется: показываются все заведения с «Понял запрос: с доставкой».
5. **Погода и попутчики уводят не туда.** Погода — в пустые новости, попутчики — в «Автомобили · Дербент» (1 034 объявления).
6. **4–5 с терпимо для явного действия «Найти», но не для холодного старта и нескольких пользователей сразу.**
   Все запросы стоят в одной очереди GPU, и отменённые на телефоне запросы продолжают её занимать.

  - Дальше `requestId` ведёт к следу в Redis (30 мин) и к полю `smart_search_feedback.request_id`.
- **Обратная связь.**
  - Путь: форма → `POST /smart-search/feedback` → запись вместе с разбором модели и уверенностью (проверено в базе).

## 4. Воспроизводимые баги

Формат каждого бага: важность · шаги · ожидание · факт · причина · слой · исправление · тест, который не даст вернуться.

### SS-01 · P0 · Варианты «Где искать?» не ведут в выбранный раздел

- **Шаги.** На экране «Поиск» ввести «Хочу покушать» → Enter → нажать «Доставка еды» (или любой другой вариант).
- **Ожидание.** Открывается выдача выбранного раздела: заведения с доставкой.
- **Факт.**
  - Раннер: 8 нажатий из 8 вернули тот же «Где искать?»; модель каждый раз отвечает `intent: unknown, domain: null`.
  - Ручное воспроизведение в одной сессии: «Объявления» → тот же вопрос; «Кино» → **1 заведение с доставкой**;
    «Новости» и «Доставка еды» → `INVALID_INTENT`, модель вернула пожелание с ключом `preferences: "покушать"`.
  - Браузер: нажатие «Доставка еды» → 4,9 с индикатора → снова «Где искать?». Сеть: запрос с сессией → `INVALID_INTENT` →
    скрытый повтор без сессии → снова уточнение. Журналы: `docs/smart-search-system-audit.json` (`taps`) и раздел 12.
- **Причина** — четыре звена сразу:
  1. Сервер: `smart-search.service.ts:282` — `if (!intent.domain || intent.intent === 'unknown')` → уточнение.
     Подсказка экрана подставляется в `domain` (`:169`), но условие по `unknown` всё равно возвращает вопрос.
     Выбор человека не учитывается.
  2. Приложение: `app/(tabs)/search.tsx:118-120` — вариант раздела отправляет **ту же фразу** с `context.screen`.
     Решение снова принимает модель, а не человек. Сессия та же.
  3. Сессия: при уточнении контекст сохраняется, если раздел определился из подсказки экрана (`service:184`).
     Следующее нажатие попадает в чужой контекст: «Кино» после «Объявлений» дало доставку.
  4. Хук: при `INVALID_*` с сессией выполняется скрытый повтор без неё (`use-smart-search.ts:84-85`).
     Время удваивается до 8–10 с, а результат — снова тот же вопрос.
- **Слой.** Сервер (маршрутизация) + приложение (обработка нажатия) + сессия.
- **Исправление.**
  - Явный выбор раздела в контракте запроса, например `context.domain` или `choice: {kind: 'domain', value}`.
    Сервер должен исполнить **прошлое намерение** (из следа по `requestId`) в выбранном адаптере без нового вызова модели —
    или вызвать модель с жёстким разделом.
  - При `unknown`, если раздел выбран человеком, вести поиск по тексту фразы в этом разделе.
  - Не сохранять контекст из ответа-уточнения о разделе.
- **Тесты.**
  - pipeline: «unknown + выбран раздел delivery» → вызван `PlacesService.list`, статус не `clarification`.
  - e2e: нажатие каждого варианта → ответ выбранного раздела.

### SS-02 · P0 · В умном поиске нет раздела заведений («поесть», «ресторан», «кафе»)

- **Шаги.** «Хочу покушать», «где поесть», «где поесть хинкал», «хороший ресторан рядом», «кафе в Каспийске».
- **Ожидание.** Заведения из существующего раздела `/places` («Доставка и заведения» на главной) без условия доставки,
  либо короткий вопрос «Ресторан или доставка?».
- **Факт.** R01 и R10 → «Где искать?». R02–R09 → раздел `delivery` с принудительным `hasDelivery=true`
  и строкой «Понял запрос: с доставкой», хотя доставку не просили. В S4 «где поесть → хинкал → в Каспийске»
  блюдо так и не применилось.
- **Причина.**
  - В реестре (`smart-search.module.ts`) четыре адаптера. Для заведений есть только `DeliverySearchAdapter`, который всегда
    ставит `hasDelivery: true` (`delivery.adapter.ts:99`).
  - В подсказке модели раздел описан как «заведения города с доставкой», подпись — «Доставка еды».
  - При этом `GET /places` умеет искать и без доставки (`placeListQuerySchema`: `types`, `cuisine`, `search`, `openNow`,
    `hasDelivery` — необязательный), а экран `places.tsx` показывает доставку переключателем.
- **Слой.** Архитектура (нет адаптера) + подсказка.
- **Исправление.**
  - `PlacesSearchAdapter` (`domain: 'places'`) на `PlacesService.list` без `hasDelivery`.
  - `delivery` — только при явной доставке или заказе.
  - Пример в подсказке «где поесть хинкал → places, dish».
  - Уточнение для «хочу покушать» — «Ресторан или доставка?».
- **Тесты.** Фразы R01–R10 в раннере; pipeline: «где поесть» → `places.list` без `hasDelivery`.

### SS-03 · P1 · «Купить» после «Хочу квартиру» → «не поддерживается», сделка теряется

- **Шаги.** «Хочу квартиру» → нажать вариант «Купить» (его предлагает сам сервер).
- **Ожидание.** Квартиры, сделка «купить».
- **Факт.**
  - «купить» → модель `intent: action` → ответ `unsupported` («Умный поиск только находит…»).
  - Следующие шаги «в Махачкале» и «до 8 миллионов» дают квартиры без сделки (цепочка S2).
- **Причина.**
  - Подсказка (`intent-prompt.ts:27`) прямо называет «купить» действием (`action`).
  - Сервис отвечает `unsupported` на любое `action` (`smart-search.service.ts:272`).
  - После `unsupported` контекст не сохраняется (`:184`).
  - Вариант «Купить» добавлен на прошлом этапе без проверки на живой модели.
- **Слой.** Подсказка + сервер.
- **Исправление.**
  - Для объявлений «купить / снять» — это сделка, а не действие. Убрать «купить» из списка `action`.
  - На сервере `action` в разделах объявлений и доставки исполнять как поиск, когда есть предмет, — с пометкой
    «оформить можно в карточке».
  - Вариант уточнения отправлять кодом (`transactionType: sale`), а не словом.
- **Тест.** Цепочка S2 в раннере; регрессия на настоящем ответе модели «купить» → `action`.

### SS-04 · P1 · «Хочу заказать пиццу» не приводит в доставку

- **Шаги.** «хочу заказать пиццу», «хочу заказать еду», «закажи суши», «хочу заказать шаурму».
- **Ожидание.** Заведения с доставкой нужного блюда и пометка «заказ — в карточке заведения».
- **Факт.**
  - D01 → `error INVALID_INTENT`: модель вернула `filters.transactionType: "order"`, у доставки такого поля нет, и
    весь ответ отклонён.
  - D05, D07, D13 → `unsupported`.
- **Причина.**
  - Подсказка доставки: «"Закажи" … — intent "action"» (`delivery.adapter.ts:266`).
  - Сервер: `action` → `unsupported`.
  - Неизвестное имя фильтра роняет весь ответ (так задумано, но `transactionType` в доставке — предсказуемая ошибка модели).
- **Слой.** Подсказка + сервер.
- **Исправление.**
  - `action` с блюдом в доставке → поиск + пометка.
  - `transactionType` в доставке → `UNSUPPORTED_BY_DOMAIN`: отбросить с пометкой, а не ронять ответ.
- **Тест.** D01–D15 в раннере; pipeline: `action` + `dish` → `places.list` вызван.

### SS-05 · P1 · Доставка: блюдо теряется, показывается всё подряд, «Понял запрос: с доставкой»

- **Шаги.** «доставка шашлыка», «доставка бургеров», «Где доставляют пиццу?».
- **Ожидание.** Поиск по блюду.
- **Факт.**
  - Модель кладёт блюдо в `category` (плитку витрины): `{"category":"пицца"}`.
  - В городе нет плиток (`GET /places/categories` → `[]`), условие уходит в `ignored`.
  - Выдача — все заведения с доставкой. Строка «Понял запрос» — «с доставкой», то есть понимание без самого запроса.
- **Причина.** `delivery.adapter.ts:157` отбрасывает неизвестную категорию и не переносит её в поиск по блюду.
- **Слой.** Нормализатор доставки.
- **Исправление.** Неизвестная плитка → `search` по блюду. Если что-то не применено, строка «Понял запрос» должна это сказать.
- **Тест.** D06, D11, D15; unit: `category: 'пицца'` при пустых плитках → `search: 'пицца'`.

### SS-06 · P1 · Цена словами и сленгом теряется или превращается в другое поле

- **Шаги.** «камри до двух миллионов»; «камри до 2 ляма».
- **Ожидание.** `priceTo` = 2 000 000 ₽.
- **Факт.**
  - L05: модель вернула `price.max 2000000`, сервер отбросил («Такого числа нет в запросе»), выдача — все Camry.
  - L24: модель прочла «2 ляма» как **объём двигателя 2 л** (`engineVolume: "2 л"`) → 0 объявлений.
- **Причина.** Сверка чисел (`normalize/amounts.ts`, `isGroundedNumber`) не знает «двух/трёх … миллионов» прописью
  и сленг «лям/ляма/лямов». Модель путает «ляма» с литрами.
- **Слой.** Сверка с фразой + модель.
- **Исправление.** Числительные прописью, «лям» в разборе сумм; правило «ляма/лям → миллион, а не литры».
- **Тест.** Unit на `amounts.ts`; L05, L24 в раннере.

### SS-07 · P1 · Новая фраза в той же сессии принимается за уточнение прошлого раздела

- **Шаги.** «Что посмотреть в кино?» → «хочу что-нибудь недорогое».
- **Ожидание.** Новый поиск: уточнение «Где искать?» или «До какой цены?».
- **Факт.** Модель: `refine/cinema` → то же расписание (S6). Экран показывает кино с пометкой «Цен билетов нет».
- **Причина.**
  - Экран «Поиск» отправляет сессию с каждой фразой (`use-smart-search.ts:66`), сброс — только по ×.
  - Сервер сливает фразу с контекстом всегда, когда модель сказала `refine`, а раздел тот же или не назван
    (`planner/query-planner.ts:246`).
  - Модель склонна говорить `refine` всякий раз, когда видит «ПРОШЛЫЙ ПОИСК».
- **Слой.** Сессия (приложение + сервер) + модель.
- **Исправление** — стратегия «продолжение / смена раздела / новый поиск / уточнение»:
  - продолжением считать короткую фразу без своего предмета («до миллиона», «а автомат?», «бензин», «в Махачкале»);
  - фразу со своим предметом или «хочу …» — новым поиском;
  - после уточнения о разделе не продолжать;
  - на экране «Поиск» — новая сессия, если прошлый ответ был не про то же.
  Не ломать задуманный сценарий «а есть дешевле?» (проверка в `smart-search-pipeline.spec.ts`).
- **Тест.** S6 в раннере; pipeline: «хочу что-нибудь недорогое» после кино → не `cinema/results`.

### SS-08 · P1 · Погода уходит в новости, хотя сервис погоды есть

- **Шаги.** «погода завтра», «будет ли дождь», «погода в Дербенте», «что по погоде завтра в Махачкале»; «какая погода».
- **Ожидание.** Прогноз из `GET /weather` и экрана `weather.tsx`.
- **Факт.** W02–W05 → новости с темой «погода» (пусто); W01 → «Где искать?».
- **Причина.** Адаптера погоды нет: GAP при наличии `WeatherService` и `/weather` (200 для всех трёх городов).
- **Исправление.** `WeatherSearchAdapter` (город + дата) и строка `SMART_SEARCH_SECTIONS` в приложении.
- **Тест.** W01–W05.

### SS-09 · P1 · «Попутчики» уводят в «Автомобили», показываются 1 034 объявления

- **Шаги.** «нужен попутчик в Дербент», «попутка до Махачкалы».
- **Ожидание.** Честное «Раздел «Попутчики» скоро» (раздела нет: на главной `ready: false`, экран `coming-soon`).
- **Факт.** `listings`, `category=transport-cars`, «Автомобили · Дербент · 25 км» — 1 034 объявления.
- **Причина.** Модель подбирает ближайшее по смыслу. Раздела и правила «попутчик → unsupported» нет.
- **Исправление.** Признак поездки → `unsupported` с текстом про раздел; позже — адаптер попутчиков.
- **Тест.** T01–T05.

### SS-10 · P1 · Скорость под нагрузкой, холодный старт, отмена не доходит до модели

- **Факт.**
  - Холодный запрос 15,4 с: `keep_alive` Ollama по умолчанию 5 минут (`/api/ps`: `expires_at` через 5 мин).
  - 5 параллельных → 4,0 / 8,8 / 12,8 / 16,5 / **20,0 с — AI_TIMEOUT**.
  - Гонка (3 фразы через 300 мс, первые две отменены клиентом) → последний ответ через **13,1 с** вместо ~4,5:
    отменённые запросы сервер продолжает гнать через модель (`ollama.provider.ts:120-126` — свой таймер без связи
    с закрытием HTTP-запроса).
- **Причина.**
  - Одна очередь GPU: 6,2 ГБ модели в 8 ГБ видеопамяти, параллельных слотов нет.
  - Повторы без кеша.
  - Подсказка ~4,3 тыс. токенов на каждую фразу.
- **Исправление** — см. раздел 11.
- **Тест.** Нагрузочная часть раннера (`concurrency`, `race`, `cold`).

### SS-11 · P2 · Экран: варианты не выглядят нажимаемыми, нет кнопки «Найти», нет выхода из петли

- **Факт.**
  - Варианты уточнения — серые плашки `surfaceMuted` (`SmartSearchBlocks.tsx:405`), визуально как текст.
  - Отправка только клавишей клавиатуры (`search.tsx:155`); если человек закрыл клавиатуру, ничего не происходит.
  - «Изменить запрос» лишь ставит фокус в поле (`:183`), сессия остаётся.
  - Нет подсказки «или напишите иначе».
- **Исправление.**
  - Варианты с акцентной рамкой (как чипсы фильтров) и строка «Можно написать по-другому».
  - Кнопка «Найти» при непустом поле.
  - «Изменить запрос» начинает новую сессию.

### SS-12 · P2 · Запасной обычный поиск на естественных фразах почти всегда пуст

- **Факт.** `GET /listings?search=<фраза>`: «Хочу тойота суксид» — 0, «…до 1.2 млн автомат бензин» — 0,
  «двушка в Махачкале» — 0, «хочу машину на автомате» — 0, «камри» — 33.
- **Причина.** Отказ модели переходит на поиск по буквам полной фразы (`ListingSmartSearch.tsx`, `search.tsx` `FallbackListings`).
- **Исправление.**
  - Запасной путь без модели: убрать служебные слова («хочу», «нужен», «ищу»).
  - Прогнать фразу через существующие подсказки (`/listings/suggest`) и классификатор заголовков — дешёвый детерминированный разбор.

### SS-13 · P2 · Условие, которое модель не смогла назвать числом, выбрасывается молча

- «нужна машина с небольшим пробегом»: модель дала `mileage.max 100000`, сверка его убрала. Сервер ответил общим вопросом
  «Какую машину вы ищете?», не упомянув пробег.
- **Исправление.** Расплывчатые условия («небольшой пробег», «недорого») — отдельным уточнением по этому полю.

### SS-14 · P2 · Разговорные формы

- «двуха» не понята. Модель: `unresolved: ["двуха"]`; помог поиск по буквам (15 двухкомнатных квартир) —
  результат верный, но случайно.
- «хинкал» одним словом → объявления с поиском «хинкал» (0) вместо заведений.
- **Исправление.** Словарь разговорных форм («двуха», «трёшка» и т. п.). Блюда → заведения (после SS-02).

### SS-15 · P2 · Скрытый повтор без контекста

- `use-smart-search.ts:84-85`: удваивает время и меняет сессию незаметно для человека.
- Нужен только после исправления SS-01, SS-07; иначе — показывать «Начать новый поиск?».

### SS-16 · P2 · Сессия глобального поиска живёт между вкладками

- Сессия хранится в памяти приложения (`smart-search-store.ts`) до ×, на сервере — 20 минут.
- Переход «Главная → Поиск» и новая фраза продолжают старый контекст (связано с SS-07).
- S7 прошёл только потому, что модель назвала другой раздел.

### SS-17 · P3 · Строка «Понял запрос» дублирует тему новостей

- «погода завтра» → «мир · 5 октября · погода · «погода»».
- Причина: `smart-search-client.ts:234` добавляет `query.text`, если нет условия `search`, а у новостей поле называется `topic`.

### SS-18 · P3 · Переходы из выдачи теряют условия

- «Всё расписание» и строка фильма открывают общий `/cinema` без даты и города.
- «Все заведения» — `/places` без блюда.
- «Все новости» — общая лента.
- Объявления передают условия корректно: через хранилище фильтров.

### SS-19 · P3 · Обратная связь

- Анализатор группирует по точной форме слова: «оперативка», «оперативки», «оперативы» — три разные группы.
- e2e `smart-search.mjs` пишет тестовое исправление в рабочую таблицу: сейчас в dev-базе 5 записей, часть — тестовые.
- Нет экрана или API для разбора статусов `new → reviewed`.

### SS-20 · P3 · Прочее

- Лимит 30 фраз в минуту на IP может срабатывать у абонентов за общим NAT оператора.
- В dev сервер доверяет `X-Forwarded-For`: аудит этим пользуется, а для боевого окружения стоит проверить `trustProxy`.
- След в Redis хранит фразу 30 минут — это нужно отразить в политике данных.

Правило выбора между самостоятельным решением и вопросом (предложение):

1. **Раздел ясен из предмета** («купить машину», «двушка», «кино», «новости», «погода», «пицца с доставкой») → сразу выдача, без вопросов.
2. **Предмет ясен, раздел неоднозначен между двумя** («хочу покушать», «где поесть») → один короткий вопрос с двумя смысловыми
   вариантами («В ресторане или с доставкой?»). Нажатие **гарантированно** исполняет поиск в выбранном разделе.
3. **Раздел ясен, предмет слишком общий** («хочу машину», «квартиру») → вопрос внутри раздела (марки, «купить / снять»)
   и вариант «Все …».
4. **Ничего не ясно** («хочу что-нибудь нормальное») → «Что ищем?» с разделами, отсортированными по смыслу,
   плюс «Искать по словам».
5. **Модель недоступна** → детерминированный разбор и поиск по словам без служебных слов.

## 13. Обратная связь

- **Путь проверен целиком:** «Я имел в виду другое» → форма (вид ошибки и текст) → `POST /smart-search/feedback` → строка
  `smart_search_feedback`.
  - Строка содержит `request_id`, `model_intent` из следа (только если фраза совпадает), `model_confidence`,
    `response_status`, `domain`, `status = new`.
  - Проверено в базе на 3 записях из приложения и e2e.
- **Лимит:** 10 в минуту.
- **Автоматических изменений нет:** подсказка до и после исправления одинакова — это проверяет unit-тест.

## 16. Рекомендованная архитектура

```
ввод (локально, без модели)
  └─ подсказки: /listings/suggest, история, категории — без модели

«Найти» ─► API /smart-search
            ├─ быстрый маршрутизатор (справочники, ключевые слова, классификатор)
            │     уверенно → адаптер раздела без модели
            ├─ кеш намерений по нормализованной фразе
            ├─ модель (очередь с пределом, отмена по закрытию запроса, keep_alive)
            ├─ решение о контексте: продолжение / смена раздела / новый поиск
            ├─ адаптеры: listings · cinema · news · delivery · places* · weather* · (rides: «скоро»)
            └─ ответ: results / clarification (смысловые варианты с кодом выбора) / no_results / unsupported / error
выбор варианта ─► API с явным выбором (раздел, сделка, марка) — исполняется без повторного разбора фразы
```

\* — новые адаптеры поверх существующих `PlacesService.list` и `WeatherService`. Своей бизнес-логики в умном поиске нет.

AI-подсказки на каждую букву не нужны. Набор текста — локальный, подсказки — существующим дешёвым `/listings/suggest`
(и аналогами разделов) с задержкой 250 мс. Полный умный поиск — только по «Найти».

## 17. Что исправлять немедленно

1. **SS-01** — явный выбор раздела в контракте и исполнение прошлого намерения в выбранном адаптере; не сохранять контекст
   из уточнения о разделе.
2. **SS-02** — адаптер заведений; «Хочу покушать» → «В ресторане или с доставкой?».
3. **SS-03, SS-04** — `action` в объявлениях и доставке исполняется как поиск; варианты уточнения отправляют код, а не слово.
4. **SS-05, SS-06** — блюдо из несуществующей плитки → поиск по блюду; числа прописью и «лям».
5. **SS-10 (часть)** — `keep_alive` и прогрев, отмена вызова модели при закрытии запроса.
