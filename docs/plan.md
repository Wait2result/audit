# Этап 0 — Анализ, архитектура и план разработки платформы «Дагестан»

## Контекст

Есть подробное ТЗ на многофункциональную платформу для жителей и гостей Дагестана: погода, кино,
новости, рестораны с доставкой, магазины, попутчики, недвижимость, чаты, отзывы, жалобы, реклама,
партнёрские кабинеты, админ-панель, аналитика. Папка проекта пуста — разработка с нуля.

Заказчик не является техническим специалистом, поэтому все термины в этом документе объясняются.
ТЗ (п. 46, 48) требует: сначала анализ и архитектура, утверждение, и только потом код.

**Цель этого документа** — закрыть Этап 0: зафиксировать стек, архитектуру, структуру БД, принципы
API, модель безопасности и защиты от DDoS, выявить противоречия и юридические блокеры, и описать,
что конкретно будет сделано на Этапе 1.

## 0. Мини-словарь (чтобы дальше всё было понятно)

| Термин | Что это |
|---|---|
| **Backend / бэкенд** | Программа на сервере. Хранит данные, проверяет права, считает деньги. Приложение на телефоне — только «витрина». |
| **API** | Набор «розеток» бэкенда, через которые приложение получает данные. Единственный способ достучаться до базы. |
| **База данных (БД)** | Хранилище таблиц: пользователи, заказы, объявления. Мы используем PostgreSQL. |
| **Монорепозиторий (монорепо)** | Один общий проект-папка, где лежат и сервер, и приложение, и админка. Общий код пишется один раз. |
| **Docker / контейнер** | «Коробка» с программой и всем, что ей нужно. Одинаково работает на вашем компьютере и на сервере. Избавляет от «у меня работало». |
| **Миграция** | Скрипт, который меняет структуру БД (добавить таблицу/колонку) без потери данных. |
| **Rate limiting** | Ограничение: не больше N запросов в минуту с одного адреса/пользователя. |
| **JWT / токен** | Электронный «пропуск», который приложение показывает серверу вместо пароля при каждом запросе. |
| **RBAC** | Права по ролям: кто что может видеть и делать. |
| **Webhook** | Обратный звонок: банк сам стучится к нам на сервер и сообщает «платёж прошёл». |
| **Фича-флаг** | Переключатель в настройках, включающий/выключающий функцию без переписывания кода. |
| **CI/CD** | Робот, который при каждом изменении кода проверяет его и выкладывает на сервер. |
| **S3-хранилище** | Отдельное «облачное» место для фото и видео. Файлы в БД не кладут — она для этого не предназначена. |
| **Скрабинг (scrubbing)** | Сервис-фильтр, через который идёт весь трафик; отсеивает атаку, пропускает живых людей. |

## 1. Утверждённые решения

| Вопрос | Решение |
|---|---|
| Мобильное приложение | **React Native + Expo (TypeScript)** — один код на iOS и Android |

## 2. Технологический стек

**Мобильное приложение**
- React Native + Expo (dev client), TypeScript
- Навигация: React Navigation; серверные данные: TanStack Query (кеш, повторы при обрыве сети,
  офлайн-поведение — прямо закрывает п. 40 ТЗ); локальное состояние: Zustand
- Хранение токенов: `expo-secure-store` (Keychain на iOS / Keystore на Android — защищённое
  системное хранилище, а не обычный файл)
- Карты: нативный SDK выбранного провайдера (см. раздел 8), внутри нашего дизайна
- Ошибки: Sentry SDK; аналитика событий: собственные события через наш же API

**Бэкенд**
- Node.js 24 + **NestJS** (TypeScript) на Fastify. NestJS выбран потому, что он изначально
  модульный — ровно как требует п. 42 ТЗ: `AuthModule`, `RidesModule`, `ChatModule` и т. д.
  Изменение одного модуля не ломает остальные.
- **PostgreSQL 17 + PostGIS** (расширение для географии: «найти всё в радиусе 3 км»)
- **Prisma** — описание схемы БД и миграции, автоматическая типизация; географические запросы —
  сырым SQL через PostGIS
- **Redis** — кеш, счётчики rate limiting, очереди задач, доставка сообщений чата
- **BullMQ** — фоновые задачи: рассылка push, обработка фото, начисление комиссий, отчёты
- **Socket.IO** (WebSocket) — чаты в реальном времени
- Валидация входных данных: Zod, схемы общие с мобильным приложением

**Веб (админ-панель + партнёрские кабинеты)**
- Next.js (React, TypeScript) — **одно приложение, два раздела**. Партнёр физически не получает
  админских данных: разделение проверяется на бэкенде, а не только скрытием кнопок в интерфейсе.

**Инфраструктура (на вашем выделенном сервере)**
- Всё в Docker Compose: API, воркеры, PostgreSQL, Redis, Nginx/Caddy (приём HTTPS), MinIO (dev)
- TLS-сертификаты Let's Encrypt, автопродление
- Бэкапы: `pgBackRest`/`wal-g` → **внешнее S3-хранилище другого провайдера** (бэкап на том же
  сервере бэкапом не является), ежемесячная автоматическая проверка восстановления (п. 4 ТЗ)
- Мониторинг: Prometheus + Grafana (нагрузка), Loki (логи), **GlitchTip/Sentry self-hosted**
  (ошибки — данные остаются в РФ), Uptime Kuma (доступность + оповещения в Telegram)
- CI/CD: GitHub Actions → сборка Docker-образов → деплой по SSH

**Файлы (фото/видео)**
Рекомендация: **арендовать S3-хранилище отдельно** (Selectel/Timeweb Object Storage, оплата за
гигабайты). Причина: на одном сервере диск — единственная точка отказа, а фото объявлений
восстановить неоткуда. MinIO используем только для локальной разработки. Итоговое подтверждение —
при заказе железа.

**Рекомендуемая стартовая конфигурация сервера:** 8 ядер / 32 ГБ RAM / 2×512 ГБ NVMe в RAID1
(зеркало дисков) + отдельный маленький VPS под staging (тестовое окружение, п. 43 ТЗ).

## 3. Архитектура системы

```
   iOS App          Android App          Админка / Кабинеты партнёров
  (React Native, один код)                       (Next.js)
        \                /                          /
         \              /                          /
          HTTPS (только через API, прямого доступа к БД нет)
                        |
              [ Nginx / Caddy — вход, TLS, лимиты ]
                        |
        ┌───────────────┴────────────────┐
        |                                 |
   NestJS API (модули)            Воркеры (BullMQ)
        |                                 |
   ┌────┴─────┬──────────┬────────────────┴──────┐
   |          |          |                        |
PostgreSQL  Redis   S3-хранилище          Внешние сервисы:
+ PostGIS  (кеш,     (фото/видео)         SMS · Push (APNs/FCM/RuStore)
           очереди)                        Карты · Meteoblue · Кино
                                           Платежи · ОРД (маркировка рекламы)
```

**Принципы:**
1. Мобильное приложение **никогда** не ходит в базу напрямую и не хранит секретных ключей (п. 46 ТЗ).
2. Все ключи внешних сервисов живут только на сервере, в переменных окружения.
3. Единая база на все города; у каждой сущности есть `city_id`. Новый город = одна строка в таблице
   `cities`, а не новая база и не новый код (п. 2 ТЗ).
4. Каждая рубрика — отдельный модуль со своими таблицами и API; общие механики (избранное, отзывы,
   жалобы, чаты, медиа) — **общие полиморфные модули**, работающие с любым типом объекта. Это
   значит: когда завтра появится рубрика «Мероприятия», избранное и отзывы для неё уже работают.

## 6. Принципы API

- REST, версионирование `/api/v1/...`, автодокументация OpenAPI/Swagger
- Единый формат ошибок: `{ code, message, details, requestId }` — `requestId` попадает в логи, по
  нему за секунду находится причина проблемы пользователя
- **Курсорная пагинация** для всех списков (п. 40 ТЗ: не грузим весь список сразу)
- **Идемпотентность** для заказов, бронирований и платежей: клиент присылает `Idempotency-Key`,
  повторный запрос не создаёт второй заказ и не списывает деньги дважды
- Публичные эндпоинты (погода, кино, новости, каталоги) работают **без авторизации** — как требует
  п. 6 ТЗ; авторизация нужна только для действий от имени пользователя
- Ответы для списков — «лёгкие» (без лишних полей), детали объекта — отдельным запросом
- Кеширование справочных данных в Redis + заголовки `ETag`

## 7. Безопасность (п. 4 ТЗ)

**Данные и доступ**
- Пароли — argon2id (современный алгоритм, устойчив к перебору на видеокартах)
- Токены: короткоживущий access (15 мин) + refresh (30 дней) с **ротацией и обнаружением кражи**
  (если старый refresh использован повторно — все сессии пользователя гасятся)
- Шифрование чувствительных полей в БД (документы водителей, реквизиты) — AES-256-GCM, ключ в
  переменных окружения/секрет-хранилище, не в коде
- База слушает **только локальную сеть сервера**, наружу не торчит вообще
- SSH только по ключам, вход под root запрещён, порт нестандартный, fail2ban
- Двухфакторная авторизация (TOTP-приложение) **обязательна** для всех админских ролей
- Журнал действий администраторов — неизменяемый, с IP и деталями
- Отдельные окружения prod / staging / dev; реальные пользовательские данные в dev не попадают
  никогда (для тестов — генератор фейковых данных)
- Автообновление зависимостей + сканирование уязвимостей (Dependabot, `npm audit`, Trivy для образов)

**Приложение**
- Валидация каждого входящего запроса (Zod) — отсекает основную массу атак
- Защита от SQL-инъекций — Prisma параметризует запросы; сырой SQL только с параметрами
- Проверка загружаемых файлов: тип по реальному содержимому, а не по расширению; лимит размера;
  пересжатие изображений (уничтожает вредоносную нагрузку внутри картинки); файлы отдаются с
  отдельного домена, чтобы загруженный HTML не мог выполниться в контексте нашего сайта
- Права проверяются на каждом запросе: «это твой заказ?» — а не «тебе не показали чужую кнопку»

## 8. Защита от DDoS — как строим (п. 50 ТЗ)

DDoS-атака — это когда на сервер направляют лавину фальшивых запросов, чтобы он перестал отвечать
живым пользователям. Защита строится **слоями**, потому что атаки бывают разного типа.

**Слой 1. Внешний фильтр (scrubbing) — подключаем перед публичным запуском**
Домен указывает не на ваш сервер, а на фильтрующую сеть провайдера (StormWall / DDoS-Guard /
Qrator). Весь трафик проходит через неё: мусор отсеивается, до вас доходит только чистый.
Это единственное, что реально спасает от объёмных атак — атаку в 100 Гбит/с ваш сервер не переживёт
никогда, каким бы мощным он ни был: захлебнётся сам канал.

**Готовим это с первого дня, даже пока фильтр не куплен:**
- реальный IP сервера считается секретом: никаких почтовых сервисов, панелей и старых DNS-записей,
  которые его раскрывают (утечка IP полностью обнуляет защиту — атакующий бьёт напрямую);
- API живёт на поддомене `api.<домен>` — переключение на фильтр = смена одной DNS-записи;
- фаервол сервера заранее умеет режим «принимать HTTP(S) только с IP-адресов фильтра».

**Слой 2. Вход на сервере (Nginx/Caddy)**
Ограничение числа одновременных соединений с одного IP, таймауты на медленные соединения (атака
Slowloris — «держим тысячу соединений открытыми и не отпускаем»), лимит размера тела запроса,
отключение неиспользуемых методов, обрыв запросов к несуществующим маршрутам.

**Слой 3. Приложение (делаю сразу, на Этапе 1)**
- Rate limiting на трёх уровнях: по IP, по пользователю, по конкретному действию
- **Отдельная жёсткая защита SMS** — это не про нагрузку, а про деньги: каждая SMS стоит вам
  рублей, и атака «шлём запросы на код тысячам номеров» сжигает бюджет за ночь. Меры: не чаще
  1 SMS в 60 секунд на номер, не более 5 в сутки на номер, лимит на IP, растущая задержка,
  капча при подозрительной активности, дневной потолок расходов с автоматическим оповещением
- Лимиты «стоимости» запроса: максимум записей на страницу, запрет тяжёлых фильтров без индекса,
  таймаут SQL-запроса
- Кеширование в Redis того, что одинаково для всех (погода, новости, афиша, главная): даже при
  наплыве трафика база не нагружается
- Все тяжёлые операции (фото, push, отчёты) — в фоновые очереди, а не в момент запроса

**Слой 4. Наблюдение и реакция**
Алерты в Telegram при всплеске 4xx/5xx, росте времени ответа, нехватке места; заранее написанная
инструкция «что делать при атаке» (включить фильтр, поднять режим повышенной строгости, закрыть
регистрацию временно); отработанное восстановление из бэкапа.

**Чего делать не надо:** покупать «защиту» на этапе разработки, когда пользователей ещё нет. Пока
о вашем домене никто не знает, атака бессмысленна. Деньги здесь тратятся к моменту публичного
запуска.

## 10. Противоречия и пробелы в ТЗ (что требует вашего решения)

1. ~~**Кино** — см. выше, главный содержательный блокер Этапа 4.~~ Решено.
2. **Комиссия с попутчиков и закон о такси (580-ФЗ).** Взимание комиссии за перевозку сближает
   сервис с агрегатором такси со всеми вытекающими требованиями. Более безопасная модель (как у
   BlaBlaCar): комиссия за сервис бронирования, а не за перевозку. **Нужна юридическая консультация
   до включения платежей** — архитектура поддержит любую из моделей.
3. **Документы водителей** — паспорта и права относятся к персональным данным с повышенными
   требованиями (шифрование, ограниченный доступ, сроки хранения, аттестованная инфраструктура).
   На выделенном сервере это выполнимо, но требует дисциплины. Проверка прав через ГИБДД
   автоматически невозможна — публичного API нет; либо ручная модерация, либо платный сервис проверки.
4. **Splash-экран 3–4 секунды** (п. 7) конфликтует с рекомендациями Apple и вредит удержанию.
   Предлагаю 1.5–2 секунды с красивой анимацией, при этом данные грузятся параллельно.
5. **Блокировка контактов (п. 18) против удобства (п. 16).** Водителю и пассажиру после
   подтверждённой поездки телефон реально нужен. Предлагаю: до подтверждения — контакты скрыты и
   блокируются, после подтверждения/оплаты — открываются автоматически внутри приложения.
6. **Публикация в сторах.** App Store и Google Play для российского разработчика — отдельный квест
   (аккаунты, оплата, проверка). Обязательно закладываем **RuStore** как третью площадку.
7. **152-ФЗ.** До запуска нужны: уведомление в Роскомнадзор об обработке персональных данных,
   политика конфиденциальности, тексты согласий, назначение ответственного. Это не код, но без
   этого запускаться нельзя.
8. **Отзывы без накруток (п. 24).** Реализую жёстко: отзыв о ресторане — только после
   завершённого заказа, о поездке — только после состоявшейся поездки. Для объектов без
   транзакции (кинотеатры) — с пометкой «без подтверждения визита».

## 11. Порядок работ

Этапы 1–22 из ТЗ сохраняются. Ближайшие три:

**Этап 1 — Фундамент** (то, что делаю сразу после утверждения плана):
1. Монорепо, TypeScript, линтеры, Git, CI
2. `docker-compose` для локальной разработки: PostgreSQL+PostGIS, Redis, MinIO
3. Схема БД (ядро): города, пользователи, роли и права, медиа, настройки, аудит; миграции;
   начальные данные — Махачкала, Каспийск, Дербент
4. Каркас NestJS: конфигурация через переменные окружения с проверкой при старте, health-check,
   логирование с `requestId`, единая обработка ошибок, Swagger
5. **Модуль Auth**: регистрация по телефону, SMS-код (в dev — в консоль), пароль argon2id,
   вход, восстановление пароля, JWT + refresh с ротацией, все лимиты и защита SMS из раздела 8
6. **RBAC**: роли Super Admin / Admin / Moderator / Support / Analyst / Technical Admin / Partner
   с конкретными наборами прав (п. 28)
7. Модуль медиа: загрузка через presigned URL, проверка типа, пересжатие и превью в фоне
8. Базовая админ-панель: вход с 2FA, управление городами, пользователями, ролями, просмотр аудита
9. `docs/SECURITY.md` и `docs/ADR/` — журнал решений

**Этап 2 — Мобильное приложение (каркас):** splash, выбор города, главная, навигация, профиль,
поиск, регистрация/вход, запрос геолокации только по факту нужды (п. 8).

**Этап 3 — Погода** — первая полная вертикаль «внешний сервис → бэкенд → кеш → экран».

**Этап 5 — Новости** — агрегатор внешних RSS: ленты «Город / Дагестан / Россия / Мир», отбор
простыми правилами, подтверждение несколькими агентствами (см. `docs/ADR/0005-новости-агрегатор.md`).

**Этап 6 — Заведения, меню и заказы** — каталог кафе, ресторанов и магазинов, меню с опциями,
корзина, оформление и статусы заказа. Меню и цены ведёт само заведение из приложения: доступ к
заведению выдаётся в панели по номеру телефона, уровни — управляющий и сотрудник
(см. `docs/ADR/0006-заведения-и-заказы.md`). Онлайн-оплаты нет — расчёт при получении.

Далее по ТЗ: платежи → партнёрские кабинеты →
попутчики → верификация → недвижимость → чаты → избранное → отзывы → жалобы → реклама → push →
аналитика → мониторинг → комплексное тестирование → production → публикация.

**Правило перехода между этапами:** следующий этап не начинается, пока в предыдущем есть
критические ошибки (п. 44 ТЗ).

## 12. Как будем проверять (верификация)

**После Этапа 1** — конкретный, проверяемый результат:
1. `pnpm install && docker compose up -d` — поднимается вся среда локально
2. `pnpm db:migrate && pnpm db:seed` — база создаётся, три города на месте
3. `pnpm test` — автотесты: регистрация, повторная отправка SMS-кода (должна упереться в лимит),
   неверный код, вход, обновление токена, кража refresh-токена, проверка прав по ролям
4. Открыть `http://localhost:3000/docs` — интерактивная документация API, каждый метод
   вызывается прямо из браузера
5. Открыть админку, войти с 2FA, создать город, увидеть запись в журнале аудита
6. `pnpm --filter mobile start` — приложение запускается на телефоне через Expo Go, логин работает

Далее после каждого этапа — прогон пользовательских сценариев из п. 44 ТЗ + автотесты на
критичные для денег места (заказы, комиссии, платежи).

## 14. Честная оценка

Полное ТЗ — это работа команды (бэкенд, мобильный разработчик, дизайнер, DevOps, тестировщик,
модераторы) на 12–18 месяцев. В одиночку с моей помощью получится, но существенно дольше, а часть
пунктов (переговоры с кинотеатрами, юрлицо, лицензии, модерация контента) вообще не решается кодом.

Архитектура в этом плане рассчитана на полное ТЗ, поэтому любой этап можно запустить раньше или
позже без переделки фундамента. Если в какой-то момент захотите выпустить рабочую версию раньше —
достаточно будет остановиться после Этапа 6 и опубликовать: погода, кино, новости, каталог
заведений, карта, поиск, избранное, отзывы и реклама уже дадут полноценное городское приложение.
