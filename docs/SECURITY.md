# Безопасность платформы «Дагестан»

Документ описывает, что уже сделано, и что обязательно нужно сделать перед
запуском в production. Соответствует пунктам 4 и 50 технического задания.

---

## 1. Что реализовано на Этапе 1

### Пароли и вход

| Мера | Как сделано |
|---|---|
| Хранение паролей | argon2id (memoryCost 19 МиБ, timeCost 2) — параметры по рекомендации OWASP. Сам пароль нигде не хранится. |
| Защита от подбора пароля | Счётчик неудачных попыток по номеру телефона; после 10 попыток — блокировка на 15 минут. Успешный вход обнуляет счётчик. |
| Защита от определения зарегистрированных номеров | Пароль проверяется даже для несуществующего пользователя (фиктивный хеш) — время ответа одинаковое. Восстановление пароля для незарегистрированного номера отвечает как при успехе, но SMS не отправляет. |
| Смена пароля | Завершает все сессии на всех устройствах. |
| Двухфакторная авторизация | TOTP-коды из приложения-аутентификатора. Секрет хранится зашифрованным (AES-256-GCM). Использованный код повторно не принимается. Неверный код считается неудачной попыткой входа наравне с неверным паролем. |

### Токены и сессии

| Мера | Как сделано |
|---|---|
| Токен доступа | JWT, срок жизни 15 минут. |
| Токен обновления | Случайные 48 байт, в базе хранится только отпечаток (HMAC-SHA256). |
| Ротация | При каждом обновлении старый токен гасится и выдаётся новый. |
| Обнаружение кражи | Повторное использование погашенного токена аннулирует всю цепочку сессий устройства и пишет запись уровня ERROR в лог. |
| Отзыв прав | Права перечитываются из базы при каждом обновлении токена — изменение вступает в силу максимум через 15 минут. |

### Коды подтверждения (SMS)

Самое дорогое место с точки зрения атаки: каждый код стоит реальных денег.
Четыре независимых ограничения:

1. Пауза 60 секунд между отправками на один номер.
2. Не более 5 кодов в сутки на один номер.
3. Не более 10 запросов в час с одного IP-адреса.
4. **Общий суточный потолок на всю систему** (`SMS_DAILY_LIMIT`) — последний рубеж
   при распределённой атаке. При достижении — запись уровня ERROR, при 80% — WARN.

Дополнительно: коды хранятся в виде отпечатка, живут 5 минут, сгорают после
успешной проверки и после исчерпания попыток ввода.

### Права доступа

- 8 ролей с конкретными наборами прав; проверка **на сервере** при каждом запросе.
- Авторизация включена глобально: открытые эндпоинты помечаются явно `@Public()`.
  Забытая пометка делает эндпоинт закрытым, а не открытым.
- У роли «Аналитик» намеренно нет доступа к персональным данным.

### Данные

- Шифрование чувствительных полей: AES-256-GCM с проверкой целостности.
- Ключ шифрования — только в переменных окружения, никогда в коде и не в базе.
- Мягкое удаление: записи скрываются, но сохраняются для разбора споров.
- Журнал действий администраторов: только добавление, с IP и идентификатором запроса.
- Из журнала и из логов автоматически вычищаются пароли, токены и коды.

### Приложение

- Проверка каждого входящего запроса по схеме (Zod); лишние поля отбрасываются —
  клиент не может дописать в запрос `isAdmin` или `roles`.
- Параметризованные SQL-запросы (Prisma) — защита от SQL-инъекций.
- Ограничение размера тела запроса: 1 МБ.
- Заголовки безопасности (helmet).
- CORS по явному списку адресов, не «всем».
- Версионирование API (`/api/v1`) — обновление сервера не ломает старые версии приложения.
- Документация API закрыта в production.
- Сервер не запускается при небезопасной конфигурации (см. `src/config/env.ts`).

## 2. Защита от DDoS

Реализовано четыре слоя, из них три работают уже сейчас.

### Слой 1. Внешний фильтр (подключается перед публичным запуском)

Домен указывает на фильтрующую сеть (StormWall / DDoS-Guard / Qrator), она
отсеивает мусор и передаёт на сервер только чистый трафик. Это единственная
защита от объёмных атак: канал сервера физически не выдержит 100 Гбит/с
независимо от его мощности.

**Подготовка, обязательная с первого дня:**

- Реальный IP-адрес сервера — секрет. Никаких почтовых сервисов, панелей
  управления и старых DNS-записей, которые его раскрывают. Утечка IP полностью
  обнуляет защиту: атакующий бьёт мимо фильтра.
- API живёт на поддомене `api.<домен>` — переключение на фильтр сводится
  к смене одной DNS-записи.
- Файрвол сервера должен уметь режим «принимать HTTP(S) только с адресов фильтра».

### Слой 2. Обратный прокси (Nginx/Caddy, настраивается при развёртывании)

Ограничение одновременных соединений с одного адреса, таймауты на медленные
соединения (защита от Slowloris), лимит размера тела, отключение неиспользуемых
HTTP-методов.

### Слой 3. Приложение — **реализовано**

- Общий лимит запросов по IP-адресу (`RATE_LIMIT_GLOBAL_PER_MINUTE`).
- Индивидуальные, более строгие лимиты на вход, регистрацию и запрос кодов.
- Отдельная многоуровневая защита бюджета на SMS (см. выше).
- Счётчики в Redis, а не в памяти процесса: при нескольких копиях сервера
  лимит остаётся общим, а не умножается на их число.
- Кеширование того, что одинаково для всех: наплыв трафика не доходит до базы.
- Ограничение размера страницы списка — запрос не может «попросить всё».

### Слой 4. Наблюдение (настраивается при развёртывании)

Оповещения при всплеске ошибок и росте времени ответа, инструкция действий при
атаке, отработанное восстановление из резервной копии.

### Важное предупреждение о доверии прокси

В `src/main.ts` параметр `trustProxy` в production должен содержать **только**
адреса собственного Nginx и фильтрующего сервиса. Если доверять заголовку
`X-Forwarded-For` от кого угодно, злоумышленник подставит произвольный адрес
и обойдёт **все** ограничения частоты — то есть отключит и защиту от подбора
паролей, и защиту бюджета на SMS.

## 3. Обязательный чек-лист перед запуском в production

### Инфраструктура
- [ ] Отдельный сервер только под production, без доступа разработчиков к данным
- [ ] SSH только по ключам, вход под root запрещён, установлен fail2ban
- [ ] База данных слушает только локальную сеть, наружу порт не открыт
- [ ] HTTPS с автопродлением сертификатов, редирект с HTTP
- [ ] Автоматические резервные копии в **другой** дата-центр
- [ ] Ежемесячная **проверка восстановления** из резервной копии (пункт 4 ТЗ)
- [ ] Подключён фильтр DDoS, IP сервера скрыт, файрвол принимает только его адреса
- [ ] Мониторинг с оповещениями в Telegram

### Настройки
- [ ] Все `CHANGE_ME` в `.env` заменены на сгенерированные значения
- [ ] `JWT_ACCESS_SECRET` и `JWT_REFRESH_SECRET` различаются
- [ ] `ENCRYPTION_KEY` сохранён в надёжном месте **отдельно от резервной копии базы**
- [ ] `SMS_PROVIDER` не `console`
- [ ] `SENTRY_DSN` настроен
- [ ] `trustProxy` содержит адреса реального прокси
- [ ] `SMS_DAILY_LIMIT` соответствует ожидаемой нагрузке

### Учётные записи
- [ ] Пароль владельца системы сменён после первого входа
- [ ] Двухфакторная авторизация включена у всех сотрудников (раздел «Безопасность» в панели)
- [ ] У каждого сотрудника отдельная учётная запись (общих не бывает)
- [ ] Права выданы по минимуму необходимого

### Юридическое
- [ ] Уведомление в Роскомнадзор об обработке персональных данных (152-ФЗ)
- [ ] Политика конфиденциальности опубликована и доступна из приложения
- [ ] Тексты согласий на обработку данных
- [ ] Назначен ответственный за обработку персональных данных
- [ ] Сервер и база физически находятся в РФ

## 4. Что делать при подозрении на инцидент

1. Не выключать сервер: логи и состояние нужны для разбора.
2. Определить, что произошло: смотреть записи уровня ERROR, особенно
   `ОБНАРУЖЕНО ПОВТОРНОЕ ИСПОЛЬЗОВАНИЕ ТОКЕНА` и достижение потолка SMS.
3. При компрометации учётной записи — заблокировать пользователя (это гасит все
   его сессии) и сменить ему пароль.
4. При компрометации сервера — сменить **все** секреты в `.env`, что автоматически
   завершит все сессии всех пользователей.
5. Записать хронологию: что, когда, кто заметил, что предприняли.
