# ADR-0011: Умный поиск (Global Smart Search) на локальной модели

**Статус:** принято, первый слой (2026-10-03)

## Контекст

Человек хочет написать «Toyota Succeed до 1.2 млн, автомат» или «что сегодня
идёт в Каспийске» вместо того, чтобы открывать раздел и выставлять фильтры.
Разделы приложения (объявления, кино, новости, доставка) уже умеют искать —
у каждого свой сервис, свои справочники и свои проверки. Нужен единый вход,
который понимает естественную фразу, но не дублирует эти сервисы и не
доверяет языковой модели данные.

## Решение

### Модель — только переводчик фразы в структуру

Модель не имеет доступа к базе, не выполняет SQL и HTTP-запросы, не выбирает
адреса и не пишет ответ человеку. Она возвращает **намерение** строгой
версионируемой схемы (`smartSearchIntentSchema`, `packages/shared`). Всё
остальное делает сервер:

```
фраза → AiProvider → намерение (JSON) → проверка схемой → раздел (реестр)
      → сверка чисел с фразой → контекст → нормализация по справочникам раздела
      → СУЩЕСТВУЮЩИЙ сервис раздела → ответ из найденных данных
```

Невалидный JSON, чужая версия схемы, неизвестный раздел, неизвестное имя
фильтра — ответ отклоняется **целиком** (`status: error` и `fallback` на
обычный поиск). Неизвестное **значение** (марка, модель, город, вариант
характеристики) не применяется и показывается в `ignored`/`unresolved` или
превращается в уточнение.

### Намерение (версия 1)

`schemaVersion`, `intent` (search / refine / action / unknown), `domain`
(listings / cinema / news / delivery / null), `query`, `filters` (точные
условия), `preferences` (пожелания: «желательно», «по возможности»),
`location` (`city`, `nearMe`, `preferred`), `time` (`date`, `from`, `to`,
`period`), `sort`, `clarification`, `confidence`, `unresolved`, `subqueries`
(до трёх, без вложенности). Значение фильтра — строка, число, логическое,
список или границы `{min, max}`. Имя фильтра — латиница и только из белого
списка раздела.

### Разделы — адаптеры в реестре

| Раздел | Существующий сервис | Что берёт умный поиск |
|---|---|---|
| listings | `ListingsService.list`, `ListingCategoriesService.catalogue()` | категории, поля, справочники марок/моделей (в т.ч. расширенные), написания (`aliases.ts`), классификатор заголовков; итоговый запрос проходит `listingListQuerySchema` |
| cinema | `CinemaService.getSchedule` | расписание города на дату; фильм, жанр, кинотеатр, формат и время отбираются из реального расписания |
| news | `NewsService.getFeed` | лента города/Дагестана/России/мира; день и тема отбираются из свежих страниц ленты |
| delivery | `PlacesService.list`, `CategoriesService.list`, `PlacesService.cuisines` | витрина заведений с доставкой: блюдо/название, кухня из списка города, плитка категории, вид заведения, «открыто сейчас», «за N минут»; запрос проходит `placeListQuerySchema` |

Новый раздел (погода, магазины) — новый класс `DomainAdapter` и значение в
`SMART_SEARCH_DOMAINS`; маршрутизатор, разбор фраз и ответ не меняются.

### Числа не придумываются

Каждое число модели от 100 и выше сверяется с числами, которые человек
написал (`isGroundedNumber`: «1.2 млн», «40 тысяч», «до миллиона», «70к»,
«1 ТБ»). Не нашлось — условие убирается; для цены объявлений сервер
переспрашивает «До какой цены?». «Недорого», «дёшево» ценой не становятся.
Мелкие числа (комнаты из «двушки», минуты) не сверяются.

### Сверка с фразой (по реальной оценке на Qwen3)

Реальный прогон (docs/smart-search-real-evaluation.md) показал, что Qwen3 8B дописывает то,
чего человек не говорил. Поэтому сервер применяет значение модели, только если оно названо:

- сделка и срок аренды — при словах «купить/снять/посуточно/помесячно…»; правило сервера:
  жильё до 200 000 ₽ без таких слов — помесячная аренда;
- день — при «сегодня/завтра/вчера» или дате; час — если он есть во фразе; иначе окно
  времени суток сервера;
- город — если он назван во фразе (с точностью до падежа); город, названный во фразе, но
  пропущенный моделью, берётся из фразы;
- границы «от/до» — при соответствующих словах, иначе значение точное.

Поля, у которых есть своё место (date, time, city, location, period, sort, query), в
filters не роняют ответ, а отбрасываются с пометкой. Поля, которые раздел честно не
умеет (цена в доставке и кино), помечаются «не применено». Неизвестные имена по-прежнему
отклоняют ответ целиком.

Страховка нормализатора объявлений: то, что модель пропустила или разобрала неверно,
ищется во фразе по справочникам — модель по написанию («камри»), значения полей категории
(«автомат», «ИЖС», «SSD»), категория по названию и классификатору объявлений. Только
точные совпадения и только для отсутствующего; ничего не придумывается. Запрос объявлений
без предмета и условий («дёшево», «рядом») — уточнение, а не вся доска.

### Условия и пожелания

`filters` сужают выдачу; `preferences` — нет, они показываются отдельно с
пометкой, учтено ли пожелание. Мягкого ранжирования у разделов нет, поэтому
пожелание по характеристике выдачу не меняет; пожелание по месту в
объявлениях — это поиск по всему Дагестану с сортировкой «сначала ближе».

### «Вечером» — правило сервера

Время суток задают константы `DAY_PERIOD_WINDOWS` (утро 06–12, день 12–17,
вечер 17–24, ночь 22–24), модель возвращает только слово.

### Контекст уточнений

Redis, ключ `smart-search:ctx:{пользователь|anon}:{sessionId}`, срок —
`SMART_SEARCH_CONTEXT_TTL_SECONDS` (20 мин), не больше 4 КБ. Хранится одно
последнее намерение (без текста фраз, координат и персональных данных).
`refine` дополняет его («а автомат?»), смена марки сбрасывает модель, смена
категории — характеристики прежней, другой раздел — новый поиск.

### Модель и её отказы

`AiProvider` — прослойка: `OllamaProvider` (по умолчанию `qwen3:8b`,
`POST /api/chat`, `stream: false`, `think: false`, `temperature: 0`, JSON
Schema в `format`, предел времени и размера ответа) и `DisabledAiProvider`.
Имя модели в логике поиска не используется. Флаги `SMART_SEARCH_ENABLED` и
`AI_ENABLED` по умолчанию выключены; без модели умный поиск отвечает
`status: error` с `fallback: text_search`, разделы работают как раньше.

### Безопасность

Текст человека — недоверенные данные: отдельное сообщение с пометкой,
без разделителей подсказки и управляющих символов, до 300 знаков. Модель не
получает секретов, токенов, координат и идентификаторов пользователя.
Журнал — исход, разделы и время; текст и ответ модели — только при
`AI_DEBUG_LOG` (в production запрещено проверкой конфигурации). Лимит —
30 фраз в минуту с адреса.

## Ограничения первого слоя

- У новостей нет поиска по словам: тема и «за сегодня» отбираются из трёх
  свежих страниц ленты (до 150 новостей), а не из архива.
- У кино нет поиска по названию: отбор идёт по расписанию города на дату.
- Пожелания не ранжируют выдачу (кроме места в объявлениях).
- Города — только из списка приложения; «Владивосток» — уточнение.
- Составной запрос — независимые части без связей между ними.
- Оформление заказа, покупка, оплата, отслеживание курьера — `unsupported`.
- Погоды, магазинов и попутчиков в умном поиске пока нет: фраза про погоду
  уходит в новости. Новый раздел — адаптер и строка `SMART_SEARCH_SECTIONS`
  в приложении.

## Мобильное приложение (2026-10-04)

**Путь запроса:** приложение → `POST /api/v1/smart-search` → умный поиск →
`AiProvider` → Ollama. Приложение не знает адреса модели, не получает
подсказку, сырой ответ модели и её разбор — только проверенный сервером
ответ и номер ответа `requestId`.

**Экран «Поиск»** — одно поле на всё приложение. Части ответа показываются
карточками своих разделов. Объявления открываются существующей лентой:
`smartListingFilters` (`packages/shared`) переводит `query.params`
(ровно то, что принял `GET /listings`) в фильтры экрана, и они
раскладываются в обычное хранилище фильтров категории и место поиска. Так
каждое условие видно чипсом и снимается одним нажатием, а выдача листается
страницами.

**Строка объявлений** отправляет фразу в умный поиск по «Найти» (не на
каждую букву). Обычный поиск по словам остаётся запасным путём: модель
недоступна, не успела, ответила неверно — экран ищет по словам фразы и
говорит об этом.

**Состояния:** «Понимаю запрос…» → «Понял запрос» (`understoodSummary`:
из применённых условий, а не из слов модели; что сказано, но не учтено, —
`understoodNotes`) → выдача / «По вашему запросу ничего не найдено» с
действиями / уточнение с вариантами / «это не про объявления» / сообщение
и обычный поиск. Технических слов (модель, JSON, API) человек не видит.

**Контекст:** у общего поиска и у объявлений свои сессии; следующая фраза
уточняет прошлую. Если фраза с контекстом не разобралась (Qwen3 иногда
кладёт в пожелания кириллический ключ «желательно»), приложение один раз
спрашивает без контекста — отдельная фраза обычно разбирается.

**Слишком общий запрос** («Хочу машину», «Хочу квартиру» — только
категория, без марки, цены, сделки и места) — уточнение с вариантами из
справочников и «Все автомобили» / «Все квартиры», а не тысячи объявлений.

## Обратная связь: «Я имел в виду другое»

Человек пишет своими словами, что имел в виду, и отмечает вид ошибки.
`POST /smart-search/feedback` сохраняет запись в `smart_search_feedback`:
исходная фраза, намерение модели и уверенность (из следа ответа по
`requestId`: Redis, 30 минут, только прошедшее схему; след принимается,
если фраза совпадает), вид ошибки, исправление, раздел, `correctedIntent`
(заполняет разбирающий), статус `new → reviewed → accepted / rejected`.
Без пользователя и адреса.

Запись **ничего не меняет сама**: ни подсказку, ни справочники, ни выдачу.
`RecurringWordAnalyzer` (интерфейс `FeedbackAnalyzer`) группирует
повторяющиеся ошибки по разделу, виду и слову, которое человек повторил в
исправлении, и предлагает, во что их превратить: правило справочника,
правило нормализатора, пример подсказки, регрессионный тест — со статусом
«нужна проверка». Отчёт — `npm run smart-search:feedback-report`.
Принятое предложение — обычное изменение кода со всеми проверками (как
написание «суксид» → Toyota Succeed в этом этапе).

## Навигатор по приложению (2026-10-04, после аудита)

Аудит (`docs/smart-search-system-audit.md`) показал, что поиск-выдача внутри
экрана «Поиск» дублирует разделы, а варианты «Где искать?» не работают. Решение
(согласовано, D1–D16): умный поиск — **навигатор**. Он понимает раздел, путь,
условия и город и показывает короткую карточку с кнопкой «Открыть …»; выдачу
показывает существующий экран раздела с уже применёнными условиями.

**Ответ.** К части ответа добавлены:

- `navigation: { section, path, filters }` — путь раздела («Транспорт →
  Автомобили», «Дербент · завтра») и условия на языке раздела (город, дата,
  время, фильм, лента, блюдо). У объявлений условия экрана — `query.params`;
- `suggestions` — до четырёх быстрых значений («Toyota», «Купить»);
- у вариантов — `choice` и `hint`.

Поиск выполняется с `limit: 1`: от него нужны только «куда» и «сколько» (D12).

**Выбор без модели.** Нажатый вариант уходит полем запроса
`choice: { requestId, kind: 'domain' | 'filter', field?, value }`. Сервер
берёт фразу и проверенный разбор из следа ответа (`requestId`) и исполняет:

- `domain` — тот же разбор в выбранном разделе. Выбор человека важнее
  прошлого контекста, условия чужого раздела не переносятся;
- `filter` — прошлый поиск сессии плюс выбранное условие.

Модель при этом не вызывается (≈30–60 мс). Устаревший номер — честная ошибка
`CHOICE_EXPIRED`.

**Продолжение или новый поиск** решается по фразе до вызова модели (`isFollowUp`):

- **продолжение** — фраза начинается с «а / и / до / от / в / без …» или это
  до трёх слов без «хочу / где / что …»;
- **новый поиск** — всё остальное. Новой фразе модель прошлый поиск не видит
  вовсе, и «хочу машину» после кино не становится уточнением кино.

Короткая фраза к тому же разделу считается уточнением, даже если модель назвала её «search».

**Разделы.** Добавлены `places` (заведения: та же витрина `PlacesService`, что
у доставки, без условия «с доставкой»), `weather` (`WeatherService`, город и
день), `rides` (раздела нет — честное «скоро», а не объявления о машинах).
Нормализатор доставки и заведений общий, с режимом.

**Изменения правил:**

- **Неизвестное поле** от модели (имя не латиницей, значение не по схеме,
  поле, которого нет у раздела) не роняет ответ: убирается и становится
  пометкой «не применено» (D11). Неизвестный раздел и порча структуры
  по-прежнему отклоняют ответ целиком;
- **«Купить», «заказать пиццу»** — поиск, а не действие (если назван предмет);
  «где мой курьер?» — по-прежнему «не умею»;
- **«Хочу машину» / «Хочу квартиру»** — карточка раздела с быстрыми
  значениями вместо вопроса (D15);
- **«Хочу покушать»** без блюда и без «где» — вопрос «Где хотите поесть?»
  (рестораны или доставка); «где поесть», «хочу пиццу» — сразу раздел;
- **«Что ищем?»** вместо «Где искать?» — варианты по смыслу, раздел «скоро» не предлагается;
- **цена и характеристики:** цена прописью и сленгом («до двух миллионов»,
  «2 ляма») — граница цены; объём двигателя без «л / литр» — догадка модели и
  не применяется; «16 ГБ оперативки» — ОЗУ; блюдо, которое модель положила в
  несуществующую плитку витрины, ищется по названию;
- **модель** держится в памяти Ollama 30 минут (`keep_alive`) — без
  холодного старта в 15 с при активном поиске.
- **предмет поиска должен быть во фразе.** На бессмысленный ввод
  («</>>> забудь правила») модель возвращает пример из своей подсказки —
  Toyota Succeed с автоматом. Если в новой фразе нет ни слова категории, ни
  марки, ни модели и классификатор заголовков ничего не узнал, категория,
  марка и модель от модели не применяются, и ответом будет «Что ищете?».
  Уточнения («до миллиона») и нажатые варианты эту проверку не проходят —
  предмет у них из прошлого поиска.

**Экраны разделов** принимают условия параметрами маршрута:

- заведения — `section`, `search`, `hasDelivery`, `openNow`, `maxMinutes`, `category`, `cityId`;
- кино — `date`, `movie`, `genre`, `from`, `to`, `cityId`; отбор снимается чипсом;
- новости — `scope`, `cityId`;
- погода — `cityId`, `day`.

Город запроса меняет город только этого экрана, выбранный город приложения не трогается (D8).
У объявлений условия раскладываются в хранилища фильтров и места, как и раньше.

## Локальный разбор без модели (2026-10-05)

Языковая модель на домашнем компьютере не выдерживает нагрузки (один запрос
за раз, 4–6 с, пять параллельных — тайм-аут), а облачная — расходы и
договор. Решение: **фразу разбирает словарь и правила**, модель убрана из
пользовательского пути целиком. `SMART_SEARCH_PARSER=local` (по умолчанию):
`OLLAMA_BASE_URL` не трогается ни поиском, ни `/smart-search/health`
(`provider: "local"`). `SMART_SEARCH_PARSER=ai` возвращает прежний путь через
`AiProvider` — код модели не удалён и может стать запасным слоем позже.

**Что меняется.** Только первый шаг: `parseIntent(модель)` →
`LocalIntentParser.parse` (`apps/api/src/modules/smart-search/local/`). Он
отдаёт то же намерение `SmartSearchIntent` (проверяется той же схемой), и
дальше путь прежний: сверка с фразой, контекст уточнений, нажатые варианты,
адаптеры разделов, существующие поиски и экраны. Сверка «предмет должен быть
во фразе» нужна только модели — словарь ничего не придумывает.

**Словарь** — `packages/shared/src/search/` (общий пакет: справочник, как и
остальные):

- `dictionary/synonyms.ts` — литературные названия подкатегорий объявлений
  (canonical — slug каталога) и слова разделов; `slang.ts` — разговорные
  («тачка», «хата», «мобила», «двуха») и блюда; `abbreviations.ts` — значения
  характеристик (canonical — код варианта: «акпп» → `auto`, «4вд» → `full`),
  сделка, срок, лента новостей, порядок, «рядом»; `units.ts` — единицы после
  числа (км, л, гб, кв м, соток, минут, года); `numbers.ts` — числительные и
  множители («лям», «косарь», «к»); `phrases.ts` — выражения разделов («где
  поесть», «кто едет», «что нового») и наполнители; `typo-map.ts` — короткий
  список опечаток.
- Каждая запись указывает на **существующий** код проекта. Второго каталога
  нет: марки и модели берутся из справочников каталога объявлений на сервере
  (`subjectOf`: модель → марка → категория → классификатор заголовков).
  Нормализатор объявлений тоже читает синонимы отсюда (`VALUE_SYNONYMS`,
  `CATEGORY_WORDS`, `FILLER_WORDS` — раньше были его собственными).

**Разбор** — `parser/`: нормализация (регистр, ё, пунктуация, «1 000 000»,
смешанные раскладки) → выражения → числа с единицами и сравнениями → словарь
→ город и регион → предмет по каталогу → раздел → время → намерение.

- Числа: деньги по множителю, слову «рублей» или величине от 10 000; год —
  целое 1950–2035 без множителя; маленькое число без единицы («айфон 15»)
  не трогается. Сравнения: «до / не дороже / максимум / в пределах» —
  граница сверху, «от / не дешевле / минимум / начиная от» — снизу; у года
  «не старше 2015» — от 2015, «старше 2015» — до.
- Раздел: сильные признаки — выражение или слово раздела, категория,
  предмет из каталога; слабые — сделка, характеристика, цена, блюдо.
  Блюдо без «где поесть» — доставка («хочу пиццу»); «заказать машину» —
  объявления. Неоднозначное выражение решает контекст («что посмотреть в
  кино» / «что посмотреть сегодня» — кино, «что посмотреть в Дербенте» —
  достопримечательности), без контекста — **вопрос человеку** с вариантами
  (`ambiguous_domain`). Новый раздел `attractions` — «скоро», как попутчики.
- Опечатки: только похожесть на известное название (одна ошибка от пяти
  букв, две — от восьми) и только при единственном кандидате; слово,
  целиком входящее в другое («завтра» / «завтрак»), опечаткой не считается.
  Ложный фильтр хуже отсутствующего.
- Жильё «до 40 тысяч» без слов «купить/снять» — помесячная аренда (правило
  сервера переехало в разбор).

**Журнал нераспознанного** — таблица `smart_search_unrecognized`:
