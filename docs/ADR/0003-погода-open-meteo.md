# ADR-0003. Источник погоды — Open-Meteo (публичный API в dev, self-hosted в production)

**Дата:** 2026-09-16
**Статус:** принято

## Контекст

`docs/plan.md` (раздел 9) оставлял источник погоды открытым вопросом:
Meteoblue (по исходному ТЗ, но платная коммерческая лицензия и обязательная
атрибуция) или Яндекс.Погода. Для Этапа 3 выбран третий вариант — Open-Meteo,
с явным требованием: в production не использовать его публичный API, а
разворачивать self-hosted инстанс (ECMWF/DWD ICON/NOAA GFS и другие модели,
смотря что доступно для нужного региона).

## Решение

**В разработке** backend обращается к публичному `https://api.open-meteo.com`
— бесплатно, без ключа, без коммерческих ограничений (использование
некоммерческое).

**В production** обязателен self-hosted инстанс Open-Meteo. Это отдельная
инфраструктурная система (проект [open-meteo/open-meteo](https://github.com/open-meteo/open-meteo)):
она сама скачивает и постоянно синхронизирует GRIB-архивы прогностических
моделей и обслуживает тот же REST API, что и публичный сервис. Вес — от
десятков до сотен гигабайт в зависимости от набора моделей и глубины
архива, плюс постоянный фоновый трафик на синхронизацию новых прогнозов.
Поднимать это в локальном Docker для разработки нецелесообразно — по
`docs/plan.md` это уровень «выделенный сервер», который арендуется на
Этапе 21–22.

**Почему это не блокирует разработку сейчас:** self-hosted инстанс отдаёт
**тот же самый API**, что и публичный — в этом весь смысл self-hosting.
Меняется только базовый URL (`OPEN_METEO_BASE_URL`), формат запроса и ответа
идентичен. `WeatherService` (`apps/api/src/modules/weather/weather.service.ts`)
написан против этого контракта и не знает, публичный сервис за ним или свой.

**Жёсткая защита от ошибки:** сервер не запустится в production, если
`OPEN_METEO_BASE_URL` всё ещё указывает на публичный домен —
проверка в `apps/api/src/config/env.ts`, по аналогии с уже существующей
проверкой `SMS_PROVIDER=console`. Так коммерческий запуск на бесплатном
публичном API невозможен по забывчивости.

## Что нужно сделать на Этапе 21–22 (провижининг сервера)

1. Поднять self-hosted Open-Meteo на выделенном сервере (или отдельном
   узле рядом с ним) — выбрать конкретные модели (ECMWF, DWD ICON, NOAA GFS,
   региональные — что реально покрывает Дагестан с нужной точностью) и
   проверить актуальные условия лицензирования данных каждой модели перед
   включением.
2. Настроить синхронизацию новых прогнозов (расписание обновления моделей).
3. Указать адрес инстанса в `OPEN_METEO_BASE_URL` — это единственное
   изменение конфигурации, код трогать не нужно.
4. Обязательно сохранить атрибуцию Open-Meteo в приложении (уже встроена —
   поле `attribution` в ответе `/weather`, показывается на экране погоды со
   ссылкой на open-meteo.com) — она нужна независимо от того, публичный
   источник или self-hosted, это условие лицензии данных.

## Кеширование и обработка недоступности

Прогноз не персистентный — кешируется только в Redis (`weather:<cityId>`,
TTL из `WEATHER_CACHE_TTL_SECONDS`, по умолчанию 15 минут), тем же способом,
что и список городов (`CitiesService`). Отдельная таблица в Postgres не
нужна: это всегда «текущий срез», а не история.

Если источник недоступен и в кеше пусто — API отвечает `502
WEATHER_UNAVAILABLE`, а не отдаёт старые данные под видом свежих: TTL кеша
и есть определение «актуально», ничего протухшего под видом текущего в
принципе оказаться не может.
